## {{CURRENT_DATE}} — 知識庫與代碼倉庫分離架構 (Repository Separation)

*   **背景 (Context)**：
    *   新專案啟動時，若將詳細的架構分析、UAT 截圖、業務筆記與日誌直接混在 Git 程式碼倉庫中，會造成代碼庫臃腫（大量二進位圖檔與非代碼文件）、Git 提交歷史混亂，且不利於 Obsidian 跨專案知識檢索。
*   **決策結論 (Decision)**：
    *   **代碼倉庫 (Repo)** 與 **知識庫 (Vault)** 物理分離：
        *   程式碼存放於獨立 Git Repo（例如 `D:\_giti3\{{PROJECT_KEY}}`）
        *   專案知識、日誌與決策存放於獨立 Obsidian Vault（`D:\_obs\obs-{{PROJECT_KEY}}`）
*   **選擇理由 (Rationale)**：
    1.  **資訊安全與權限隔離**：知識庫中可能包含架構草稿、內部密鑰指引或會議筆記，與開源或團隊 Git 代碼權限分開。
    2.  **AI 脈絡純化**：AI 在閱讀知識庫時不被數萬行 vendor / node_modules 代碼干擾；在寫代碼時透過 `CLAUDE.md` 精準導航。
    3.  **Obsidian 雙向連結體驗最佳**：專注於 Markdown 與長期記憶管理。

## {{CURRENT_DATE}} — 專案長期記憶「context」四層分流架構

*   **背景 (Context)**：
    *   隨專案推進，單一 `docs/` 資料夾容易堆積數十個文件，導致日常查看的待辦和工作日誌被淹沒。
*   **決策結論 (Decision)**：
    *   建立 `_docs/context/` 長期記憶目錄，並細分為 4 大板塊：
        1. `01_規劃與計畫/`（統一加上 `Plan_` 前綴 + 決策紀錄）
        2. `02_技術研究與分析/`（統一加上 `Research_` 前綴）
        3. `03_工作紀錄與驗證/`（統一加上 `Walkthrough_` 前綴）
        4. `04_維運與部署/`（SOP、Checklist、工作流規範）
*   **選擇理由 (Rationale)**：
    1.  **日常看板乾淨**：根目錄保持極簡，一秒掌握今日進度。
    2.  **立體化記憶鏈**：從「計畫 (Plan) ➔ 研究 (Research) ➔ 驗證 (Walkthrough) ➔ 部署 (Deploy)」形成完整的可溯源鏈條。
