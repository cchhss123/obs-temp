# 專案工作流管理議題與工程規範

> 本文件梳理專案在多倉庫協作、版本控制、舊系統資料庫保護與 AI 輔助開發過程中的核心治理規則。

---

## 📌 議題一：Git 分支與多倉庫審查策略 (Branching & Multi-Repo Review)

*   **多倉庫分支對齊架構**：
    *   **`main` 分支**：對應正式機 / 雲端測試機，所有關聯倉庫（Frontend / Backend / Admin）的 `main` 分支必須經過聯調測試後方可合併，始終保持「最穩定、可發布」狀態。
    *   **`dev` / `feature-*` 分支**：本地端日常功能開發與除錯。
*   **人工審查原則 (Human-in-the-Loop)**：
    *   AI 助手修改之代碼僅留於本地暫存。
    *   所有 `git commit` 說明與 `git push` 必須由專案負責人手動審查（Code Review）後親自執行，避免未驗證腳本自動提交造成跨倉庫版本不一致或 Regression。

---

## 📌 議題二：UAT 測試與舊系統資料庫保護防線 (Database Protection)

*   **唯一真實來源 (Source of Truth 防線)**：
    *   一旦進入測試或正式運作，雲端/測試伺服器上的資料庫即為業務真實數據來源。
    *   **嚴格禁止**從本地用 `.dump` 任意覆蓋伺服器資料庫，防止業務數據遺失。
*   **Schema 遷移與防腐層規範**：
    *   若是舊系統新模組：**絕對禁止直接修改舊核心資料表結構**。
    *   一律使用 Migration 腳本（以追加新表、獨立 Schema 或向後相容欄位方式）。
    *   結構變更前必須先行執行資料庫快照備份。

---

## 📌 議題三：Hub-and-Spoke 雙層日誌同步規範

*   本知識庫記錄「深度代碼、API 變更與技術除錯細節」。
*   每日工作結束時，由 AI 產出 1~2 行「高階里程碑摘要」，手動貼回 `workIdeax` 或 `obs-and`，維持總駕駛艙的全域視角。

---

## 📌 議題四：知識庫雙向連結健康度維護

*   新增或重命名 Markdown 檔案時，需確保其對應到 [[_docs/context/00_長期記憶導覽索引|00_長期記憶導覽索引]] 中的 MOC 表格。
*   保持檔案開頭的 `Plan_`、`Walkthrough_`、`Research_` 前綴統一，讓知識檢索維持極高可讀性。
